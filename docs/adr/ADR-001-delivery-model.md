# ADR-001: Выбор модели поставки проекта CyberClub

**Статус:** Принято

## 1. Контекст

CyberClub — информационная система для бронирования и управления компьютерным клубом.

Основные пользователи системы:
- клиент компьютерного клуба;
- администратор компьютерного клуба.

Проект разрабатывается в рамках учебного курса «Управление IT-проектами».

На начальном этапе определены основные функции системы, однако требования могут уточняться и изменяться в процессе разработки.

Проект выполняется одним разработчиком, поэтому важно иметь возможность быстро изменять приоритеты и постепенно добавлять функциональность.

## 2. Драйверы решения

При выборе модели поставки учитывались следующие факторы:

- небольшой размер проекта;
- разработка одним человеком;
- возможность изменения требований;
- необходимость получать работающий результат поэтапно;
- ограниченный срок учебного семестра;
- отсутствие жёсткого коммерческого контракта;
- возможность демонстрировать промежуточные версии системы.

## 3. Рассмотренные варианты

### Вариант 1. Predictive

При Predictive-подходе весь объём работ, требования и сроки определяются заранее.

**Преимущества:**
- понятный план проекта;
- заранее определены этапы и сроки;
- проще контролировать выполнение первоначального плана.

**Недостатки:**
- сложно быстро менять требования;
- ошибки в первоначальных требованиях могут обнаружиться поздно;
- для небольшого учебного проекта требуется слишком много предварительного планирования.

### Вариант 2. Hybrid

Hybrid сочетает предварительное планирование и гибкую разработку.

**Преимущества:**
- основные этапы можно определить заранее;
- внутри этапов можно гибко менять задачи;
- подходит для проектов с фиксированной частью требований.

**Недостатки:**
- для небольшого проекта усложняет управление;
- необходимо одновременно поддерживать два подхода;
- преимущества Hybrid для проекта CyberClub не являются критичными.

### Вариант 3. Adaptive

При Adaptive-подходе система создаётся небольшими итерациями, а требования и приоритеты могут уточняться в процессе работы.

**Преимущества:**
- можно быстро реагировать на изменение требований;
- работающий результат появляется постепенно;
- можно сначала разработать самые важные функции;
- удобно использовать короткие итерации и GitHub Projects;
- хорошо подходит для небольшого проекта.

**Недостатки:**
- конечный объём функций может меняться;
- сложнее заранее определить точную дату завершения каждой функции;
- необходимо регулярно пересматривать приоритеты.

## 4. Решение

Для проекта CyberClub выбрана модель **Adaptive**.

Разработка будет выполняться небольшими итерациями.

Сначала будут реализованы основные функции:

1. регистрация и авторизация;
2. просмотр компьютеров;
3. просмотр свободного времени;
4. бронирование компьютера;
5. управление бронированиями.

После получения работающей базовой версии функциональность системы будет постепенно расширяться.

Задачи и их приоритеты будут управляться через GitHub Projects.

## 5. Последствия решения

### Положительные последствия

- можно быстро менять требования;
- работающая версия системы появляется раньше;
- основные функции можно реализовать в первую очередь;
- легче исправлять ошибки на ранних этапах;
- удобно организовать работу через короткие итерации.

### Отрицательные последствия

Выбирая Adaptive, мы отказываемся от полностью фиксированного плана проекта.

Это означает, что:
- состав второстепенных функций может изменяться;
- некоторые запланированные функции могут быть перенесены;
- необходимо регулярно пересматривать бэклог;
- заранее невозможно гарантировать реализацию абсолютно всех желаемых функций.

Несмотря на эти ограничения, Adaptive наиболее подходит для небольшого учебного проекта CyberClub.
